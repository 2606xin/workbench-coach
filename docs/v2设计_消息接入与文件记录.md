# v2 设计：消息接入（飞书 / 企微 / 钉钉）与本地文件改动记录

> 姊妹篇：[《一、历史对话消息获取方案：国人常用对话软件》](v2设计_一_历史消息获取_国人对话软件.md)——微信/QQ 等个人聊天软件的合规分层与导入格式。
> 状态：设计稿（2026-11-11），基于真实调研。目标读者：维护者与贡献者。
> 原则不变：**范围由用户勾选 → 授权留痕 → 增量拉取 → 本地脱敏 → 只把素材包交给 AI**。专门的事交给专门维护的开源项目（同 agent-dump 哲学）。

## 一、v1 现状与 v2 蓝图

| 层 | 通道 | v1 状态 | v2 目标 |
|---|---|---|---|
| L0 | 本地 AI 会话（agent-dump） | ✅ | 持续跟随上游 |
| L0 | 本地文件夹 / 收集箱 | ✅ | 文件夹升级为「带改动记录的监控源」 |
| L1 | 钉钉 | v2 占位灰卡 | **Stream 模式机器人收件箱**（免费、无需公网） |
| L1 | 飞书 | v2 占位灰卡 | **官方 lark-openapi-mcp 拉取会话** |
| L1 | 企业微信 | v2 占位灰卡 | **自建应用机器人收件箱**（免费）；会话存档仅作企业付费选读 |
| L2 | 本地文件改动记录 | 无 | watchdog 守护 + git log 零依赖路径 |

设计不变式：**任何新通道都只是「素材包的上游」**——数据先进本机、脱敏后才进上下文；凭证永不写入任何文件（Keychain / 环境变量）。

## 二、选型矩阵（2026-11 调研结论）

| 通道 | 选用项目 | 官方性 | 协议 | 形态 | 权限要求 | 结论 |
|---|---|---|---|---|---|---|
| 飞书 | [larksuite/lark-openapi-mcp](https://github.com/larksuite/lark-openapi-mcp) | 官方 | MIT | npx 运行的 MCP Server（TS） | 开放平台建自建应用 + App ID/Secret + API 权限；机器人进群后可 `im.v1.message.list` 拉消息 | ✅ 选用。引导到「创建应用→加权限→进群」三步，凭证进 Keychain |
| 钉钉 | [open-dingtalk/dingtalk-stream-sdk-nodejs](https://github.com/open-dingtalk/dingtalk-stream-sdk-nodejs)（另有 Python/Go/Java 版）+ 官方机器人消息 MCP | 官方 | 开源（MIT 类） | Stream 模式 SDK：事件/机器人收消息**无需公网回调地址** | 组织内建机器人（个人可免费建团队） | ✅ 选用。Stream 长连接收消息 → 写本地收件箱 → 走现有收集管道 |
| 企业微信 | 自建应用「接收消息」回调；群机器人 webhook 仅发（已用于 push） | 官方 API | — | 回调接收用户发给应用的消息 | **需企业管理员**创建自建应用并配可信域名/IP | ✅ 收件箱模式。免费、合规、够用 |
| 企业微信（企业级） | 会话存档 msgaudit（官方 C SDK，社区有 Go/Java 封装） | 官方 | 付费 | C 动态库（仅 Linux/Windows），RSA 解密 | 管理员开通 + 员工/客户知情同意，约 450 元/人/年 | ⛔ 不做默认路径。文档标注为企业付费选读，代码不内置 |
| 文件改动 | [watchdog](https://github.com/gorakhargosh/watchdog)（Python） | 社区标准 | Apache-2.0 | 库 + watchmedo 命令；macOS 用 FSEvents 原生 API | 无 | ✅ 选用。守护进程写 SQLite 日志，collect 读日志 |
| 文件改动（git 仓） | git log / diff | — | GPL 但作为外部命令调用无传染 | 外部命令 | 无 | ✅ 零依赖路径：文件夹是 git 仓时直接读历史，不必装 watchdog |
| （对比）fswatch | — | — | **GPL-3** | 命令行 | 无 | ❌ 协议传染性，放弃 |
| （备选桥）n8n 自托管 | n8n（含飞书/企微/钉钉节点） | 社区 | **fair-code（非 OSI）** | 可视化自动化 | 各通道凭证 | 🔶 高级选读：作为「已经有 n8n 的用户」的桥接配方，不进核心 |

> 个人微信：维持 v1 立场不接（无合规接口，不用第三方外挂）。

## 三、引导式配置设计（`workbench.py connect`）

延续 pick 页面「不勾不读、必须同意」的最小授权哲学，新增 `connect` 向导，每通道一段：

```
python3 scripts/workbench.py connect feishu
  1) 检测：Node.js ≥ LTS？（没有 → 给安装指引或跳过）
  2) 引导：打开开放平台建应用的三步图文（建应用→开权限→拉机器人进群）
  3) 粘贴凭证：App ID / Secret → 只写 macOS Keychain（Win: 凭据管理器），不落文件
  4) 自检：拉 1 条最近消息成功 → 显示「已连通」；失败则原样报错并停在向导
  5) 授权留痕：通道与范围写进 scope.json（pick 页面第①部分出现新卡片，可勾/可撤）
```

- pick 页面第①部分为每个已连通通道显示一张卡：来源、上次同步时间、可撤回授权（删 Keychain 条目 + scope 标记）。
- 与「按场景找技能」的白名单机制复用：MCP 类通道（飞书）默认走官方源；其余通道不涉及。

## 四、采集器架构（connectors）

```
connectors/
  feishu.py     # 调 npx lark-mcp 拉群消息（进程外、超时保护）
  dingtalk.py   # Stream SDK 收消息 → 写 工作台/收集箱/dingtalk/日期.jsonl
  wecom.py      # 回调收件箱（本地起一次性 HTTP 接收，同 pick 页面机制）
  filewatch.py  # watchdog 守护（可选安装）→ 工作台/文件日志.sqlite
  gitlog.py     # git 仓历史读取（零依赖，纯 subprocess）
```

- 全部**可选依赖**：某个 connector 的依赖没装，`detect` 里如实标注「未安装，跳过」，主流程不受影响（同 agent-dump 降级模式）。
- 游标与遮挡复用现有 `state.json` / `Redactor`；消息类通道只取「用户发的内容 + 时间 + 群名」，跳过系统消息。
- 文件改动记录双路径：git 仓直接 `git log --since=<游标>`（改动文件 + 摘要）；非 git 文件夹用 watchdog 日志（事件类型/路径/mtime，**不记录内容**，内容仍按授权范围读取）。

## 五、路线图（每步独立可发布）

| 版本 | 内容 | 验收 |
|---|---|---|
| **v2.0** | **聊天记录导入解析器**（CSV/JSON/TXT/HTML 四形态，按姊妹篇 §3 规范）＋**自动分类**（按群/联系人归组为 project，进素材包与项目索引）＋ `import` 向导化 | 任选一个主流导出工具的产物（含 PyWxDump 系 Web 导出、Telegram 官方导出）→ import → 素材包按会话方分组、脱敏、增量不重复 |
| v2.1 | 钉钉 Stream 收件箱 + connect 向导 | 个人免费团队实测：发消息给机器人 → 下次 collect 进素材包（已脱敏） |
| v2.2 | 飞书 lark-mcp 拉群消息 + connect 向导 | 拉到指定群最近 N 条，凭证仅存 Keychain |
| v2.3 | 企微自建应用收件箱（需管理员，课堂标注） | 收到用户发给应用的消息进素材包 |
| v2.4 | 文件改动记录（gitlog 零依赖 + watchdog 可选）＋ 素材包「文件改动」区块 | 非 git/git 两种文件夹各跑通增量；未装 watchdog 全流程不受影响 |
| v2.x | n8n / AstrBot 桥接配方（文档级）、更多通道按同一模式扩展 | — |

> 优先级依据（2026-11-11 与维护者对齐）：**主需求＝获取历史记录用于学习＋分类整理**——故聊天记录导入升为 v2.0，文件记录后移 v2.4。

## 六、合规与许可注意

- 三通道全部走**官方 API**；企微会话存档与个人微信外挂明确不进默认路径。
- 引用项目协议：lark-openapi-mcp（MIT）、dingtalk-stream SDK（MIT 类）、watchdog（Apache-2.0）——与本仓库 MIT 兼容，致谢清单将随代码更新。
- 凭证一律进系统凭据库；素材包与输出物中出现的任何令牌由现有 `Redactor` 兜底遮挡。

## 七、配置复杂度对照（估算，2026-11）

| 通道 | 谁能配 | 步骤概要 | 预计耗时 | 最大卡点 |
|---|---|---|---|---|
| 钉钉 | 个人（免费建团队） | 建应用→拿 Client ID/Secret→开机器人→Stream 收消息，无需公网 | 10–15 分钟 | 几乎没有 |
| 飞书 | 个人开发者＋免费测试企业 | 建应用→App ID/Secret→申请消息读取权限（部分需审批）→机器人进群→`npx lark-mcp` | 15–30 分钟 | 权限审批；真实企业需管理员发布；机器人只读所在群 |
| 企业微信 | 需企业；个人注册后回调仍难 | 建自建应用→**公网可信域名回调＋加解密** | 1–2 小时起 | 公网回调硬门槛（个人需内网穿透）；企业内已配好则学员侧近零配置 |

`connect` 向导能把这些步骤引导化（检测→图文→粘贴凭证→自检），把 15 分钟压到 5 分钟；**审批类等待压不掉**，页面上要有「等待审批」的中间态。

## 八、历史深度预期（用户要问的「能拿到多少」）

| 来源 | 历史深度 |
|---|---|
| 官方通道（A 层） | 机器人/应用**可见范围**：新消息为主＋有限历史（飞书可拉机器人所在群一段历史；企微应用基本只有配置之后的来信） |
| 本地 AI 会话 | 全量（实测 1376 会话） |
| 微信/QQ 本地库（B 层） | 技术上可到全量文本消息级；实际受工具断档＋法律灰区制约（详见姊妹篇 §1） |
| iMessage / Telegram / WhatsApp | 全量（本机明文库 / 官方导出） |

契约不变：**import 管道不挑源头——文件里有多少，素材包就有多少。**
